# Research: Reimplementing Vista/7-era WDM USB audio drivers (busb2902.sys / busbwdm.sys) on Windows 10/11 (24H2+)

## Summary
The legacy building blocks still exist on Win10/11: USBD.SYS exports used by busb2902.sys are deprecated-but-functional, and PortCls WaveCyclic/WavePci miniports are still shipped (docs say "no longer recommended, use WaveRT", no removal date). But the practical path is a signed KMDF driver: raw WDM+USBD is deprecated, WaveCyclic miniport work is throwaway, and kdmapper is not viable for a real USB client driver (vulnerable-driver blocklist on by default since Win11 2022 update; mapped driver has no PnP/FDO node, so it cannot bind to hardware or be a USB client). Recommended PoC: KMDF driver claiming the PCM2902 via INF over usbaudio.sys, isoch URBs, custom DeviceIoControl protocol reusing the original ASIO DLL (Option A) — or zero-kernel-driver (Option C) if the original IOCTL surface can be re-exposed as a user-mode wrapper.

## Findings

### 1. USBD.SYS direct-import status on Win10/11
- **Claim:** The USBD interface is deprecated, not removed. `USBD_GetUSBDIVersion` is deprecated (replaced by `USBD_IsInterfaceVersionSupported`); `USBD_CreateConfigurationRequest` is deprecated (replaced by `USBD_CreateConfigurationRequestEx`); the deprecated list also includes `USBD_CalculateUsbBandwidth`, `USBD_QueryBusTime`, `USBD_ParseConfigurationDescriptor`, `USBD_RegisterHcFilter`, `USBD_Debug_LogEntry`. `USBD_CreateConfigurationRequestEx` and `USBD_ParseConfigurationDescriptorEx` are NOT deprecated and still work.
- **Sources:** [Usbdlib.h reference](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/usbdlib/), [Deprecated USB routines/IOCTLs](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/_usbref/), [USBD_SelectConfigUrbAllocateAndBuild](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/usbdlib/nf-usbdlib-usbd_selectconfigurballocateandbuild)
- **Support:** direct evidence (MSDN notes: "USBD_IsInterfaceVersionSupported replaces the USBD_GetUSBDIVersion routine"; "In Windows 8, USBD_SelectConfigUrbAllocateAndBuild replaces USBD_CreateConfigurationRequestEx").
- **Confidence:** high that it's deprecated and still shipped; **medium** that the old binary compiles/links unmodified on current WDK — the deprecated WDM path is explicitly not recommended for new drivers, and under xHCI (USB 3.0 stack, all Win10/11-era controllers are xHCI) some legacy routines (e.g. `USBD_CalculateUsbBandwidth`, `USBD_QueryBusTime`) are no-ops or lack xHCI support. Reimplementation should use modern replacements: `USBD_CreateHandle`, `USBD_SelectConfigUrbAllocateAndBuild`, `USBD_IsochUrbAllocate`, or the KMDF equivalents.
- **Replacement guidance:** Microsoft's modern USB stack architecture routes xHCI through KMDF-based USB 3.0 stack ([USB 3.0 driver stack architecture](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/usb-3-0-driver-stack-architecture)); WDM clients still work through the USBD compatibility layer, but KMDF (`WdfUsbTarget*`) is the recommended client interface. `usbaudio.sys` remains the class-driver alternative.

### 2. PortCls WaveCyclic/WavePci miniport status
- **Claim:** Still shipped in Win10/11. Docs mark WaveCyclic and WavePci "no longer recommended, instead use WaveRT"; WaveRT is the preferred port since Vista. `PcNewMiniport` with `CLSID_MiniportDriverWaveCyclic` still documented. No deprecation/removal timeline published.
- **Sources:** [WaveCyclic Port Driver](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/wavecyclic-port-driver), [Wave Filters](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/wave-filters), [PcNewMiniport](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/portcls/nf-portcls-pcnewminiport), [Introducing the WaveRT Port Driver](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/introducing-the-wavert-port-driver)
- **Support:** direct evidence for "no longer recommended"; researcher inference for "no removal announced, but any new work on WaveCyclic is throwaway."
- **Confidence:** high.

### 3. Custom USB audio driver for PCM2902 + KMDF isoch + kdmapper viability
- **Claim (INF override):** Viable. A third-party INF matching the device hardware ID (`USB\VID_08BB&PID_2902...`) or the generic compatible ID binds the custom driver instead of `usbaudio.sys` (Wdma_usb.inf) — Microsoft documents that a third-party driver on the system/Windows Update overrides the class driver (stated for usbaudio2.sys; same PnP precedence applies to UAC1). Requires a signed driver package (see Q4).
- **Sources:** [USB Audio 2.0 driver doc (override statement)](https://github.com/MicrosoftDocs/windows-driver-docs/blob/staging/windows-driver-docs-pr/audio/usb-2-0-audio-drivers.md), [usbaudio.sys](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/usb-audio-class-system-driver--usbaudio-sys-)
- **Support:** direct evidence for override mechanism; inference that UAC1 behaves identically (standard PnP rank rules).
- **Claim (KMDF isoch):** KMDF supports isochronous, but NOT via the continuous reader: "You can configure a continuous reader for a bulk pipe or an interrupt pipe" — isoch pipes return `STATUS_INVALID_DEVICE_REQUEST`. Isoch requires `WdfUsbTargetDeviceCreateIsochUrb` + `WdfUsbTargetPipeWdmGetPipeHandle` + manual `_URB_ISOCH_TRANSFER` (with `USBD_START_ISO_TRANSFER_ASAP`), or `WdfUsbTargetPipeReadIsochPayloadAsap`/`WriteIsochPayloadAsap`. Reference sample: USBSAMP.
- **Sources:** [WdfUsbTargetPipeConfigContinuousReader](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdfusb/nf-wdfusb-wdfusbtargetpipeconfigcontinuousreader), [Isoch endpoint transfers](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/transfer-data-to-isochronous-endpoints), [WdfUsbTargetDeviceCreateIsochUrb](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdfusb/nf-wdfusb-wdfusbtargetdevicecreateisochurb)
- **Support:** direct evidence. **Confidence:** high.
- **Claim (kdmapper):** Not viable for this driver. (a) Manual mapping is anti-pattern territory on 24H2+: the Microsoft vulnerable driver blocklist is on by default since the Win11 2022 update and is enforced whenever HVCI/Memory Integrity, Smart App Control, or S mode is active — kdmapper's exploit drivers (iqvw64e.sys etc.) are blocked; multiple kdmapper issues report breakage on Win11 22H2+. (b) Architecturally, kdmapper loads a driver image with no PnP device node/FDO in the device tree: `IoCreateDevice` can create a raw control device and expose a device interface, but a USB client driver needs a PnP-enumerated PDO, select-configuration through the hub PDO, and INF binding — none of which a mapped image gets. A mapped driver cannot become the function driver for the PCM2902.
- **Sources:** [Microsoft recommended driver block rules](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/windows-defender-application-control/design/microsoft-recommended-driver-block-rules), [kdmapper issue #122](https://github.com/TheCruZ/kdmapper/issues/122), [kdmapper issue #175](https://github.com/TheCruZ/kdmapper/issues/175), [kdmapper repo](https://github.com/TheCruZ/kdmapper)
- **Support:** direct evidence for blocklist default/strong HVCI link (block rules doc); kdmapper-no-PnP implications are researcher inference from documented PnP architecture. **Confidence:** high for blocklist, medium for exact 24H2 behavioral deltas (no published MS doc on kdmapper specifically).

### 4. Driver signing on Win10/11 x64
- **Claim:** Kernel-mode drivers must be signed. Production path: Microsoft attestation signing or WHQL via Partner Center (cross-signing is dead; EV cert + dashboard). Test path: `bcdedit /set testsigning on` allows test-signed drivers (self-signed cert, run under `bcdedit /set loadoptions DDISABLE_INTEGRITY_CHECKS` is legacy/unnecessary); testsigning disables the desktop watermark tradeoff only. With testsigning ON, a test-signed KMDF driver installs normally via `pnputil /add-driver driver.inf /install` or Device Manager ("Have Disk").
- **HVCI interaction:** When Memory Integrity (HVCI) is on (default on most new Win11 devices), even with testsigning, drivers must meet HVCI code-integrity requirements (no executable+writable memory, no MS internal kernel APIs, etc.); test-signed drivers CAN load under HVCI with testsigning enabled, but only if they are HVCI-compatible. When HVCI is on, the vulnerable driver blocklist is enforced regardless of testsigning. Disable HVCI in Windows Security for a dev box if the driver uses non-conforming constructs.
- **INF vs KMCS:** INF must be signed too, but for a dev box the INF can carry an unsigned catalog IF testsigning is on; WHQL/attestation signing is required only for shipping (Secure Boot + non-testsigning boot).
- **kdmapper + HVCI:** explicitly incompatible; mapped code pages fail HVCI checks. Not a signing strategy.
- **Sources:** [Attestation signing](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/code-signing-attestation), [Driver code signing requirements](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/code-signing-reqs), [HVCI enablement](https://learn.microsoft.com/en-us/windows-hardware/design/device-experiences/oem-hvci-enablement), [Vulnerable driver blocklist](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/windows-defender-application-control/design/microsoft-recommended-driver-block-rules)
- **Support:** direct evidence for signing paths and HVCI/blocklist defaults; HVCI-conformance requirement details (no W+X, no internal APIs) come from HVCI docs interpretation — medium confidence on exact per-rule wording.
- **Confidence:** high overall.

### 5. Architecture recommendation for the PoC
Ranked:
1. **Option C (first 30 min): in-box `usbaudio.sys` (UAC1) + custom ASIO DLL over WaveRT/KS.** PCM2902 is UAC1; usbaudio.sys is still shipped in Win11 ([supported USB classes](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/supported-usb-classes), [usbaudio.sys doc](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/usb-audio-class-system-driver--usbaudio-sys-)). ASIO4ALL-style: ASIO DLL talks to KS pins/WaveRT via user-mode kernel streaming (KsOpenDefaultDevice, IKsControl, pin handshake + RT buffer). Zero kernel code, zero signing, works under HVCI immediately. Downside: latency = WaveRT clock + usbaudio.sys isoch scheduling; limited control over the exact DMA/period behavior the original busb2902.sys had.
2. **Option A: signed KMDF driver + isoch URBs + DeviceIoControl reusing original ASIO DLL.** Most faithful to the original busb2902.sys: KMDF control-device + `WdfUsbTargetDeviceCreateIsochUrb`/`WdfUsbTargetPipeReadIsochPayloadAsap` pumping, ring buffer, IOCTLs named/numbered to match the original ASIO DLL's expectations. Requires INF override over usbaudio.sys (hardware-ID match, rank above Wdma_usb.inf's compatible-ID match) and test/attestation signing. This is the practical "reimplementation" answer.
3. **Option B: KMDF + WaveRT miniport (portcls).** Only if the goal is a standard audio endpoint for arbitrary Windows apps (WASAPI/Shared). Correct modern combo: PcRegisterAdapter... with a **WaveRT** (not WaveCyclic) miniport + KMDF lower edge doing the USB isoch. Highest effort; the original busbwdm.sys's WaveCyclic miniport must be rewritten as WaveRT anyway, so the original miniport code is mostly unusable.

**Verdict:** start with C to validate the ASIO DLL surface and audio quality; build A as the real deliverable (it's the only option that reuses the original ASIO DLL's custom IOCTL protocol); do B only if a shared-mode Windows audio endpoint is a requirement. Never kdmapper.
- **Support:** architecture ranking is researcher synthesis from the sources above.

## Contradictions
- kdmapper.com's "KDMapper on Windows 11" page is SEO filler claiming conditional/variable success with no specifics; contradicts MS blocklist doc (blocklist on by default, enforced under HVCI) and kdmapper's own GitHub issues (#122, #175) showing failures on 22H2+. Side with MS docs + GitHub issues.
- No contradiction found on USBD deprecation or WaveCyclic recommendation.

## Missing evidence
- No Microsoft page explicitly states "legacy WDM USBD imports are removed/blocked in Win11 24H2" — status is documented only as deprecated; binary-level verification on 24H2 requires compiling a test WDM driver (unverified here).
- Whether `usbaudio.sys` on Win11 exposes KS pins with the same topology/layout assumptions the original ASIO4ALL-style DLLs relied on — needs runtime testing.
- Exact HVCI conformance rule list for the planned KMDF driver (executable-writable pages, pool tags) — verify with `MSINFO32` + SDV/HVCI-compatible build flags.
- 24H2-specific changes to portcls or usbaudio.sys — none found in public docs.
